# แผนรอบ issue #6

รอบนี้ทำให้ Jaana รับโจทย์จาก stress test 71 เคสใน issue #6 ได้ ผู้ได้ประโยชน์คือแม่ค้าที่แปะแชทลูกค้าเข้าเดโมหรือเข้าไลบรารี แล้วต้องได้ที่อยู่ที่ไม่ผสมข้ามคน ไม่ทิ้งหมายเหตุการส่ง ไม่ตัดเบอร์เงียบ ๆ และได้ช่องแอดมินครบเมื่อ gazetteer ชี้ได้ที่เดียว

## ผลตรวจ issue #6 กับโมเดลที่ ship อยู่

รันเมื่อ 16 พ.ย. 2026 บน `2dca76f` ด้วย `createTaggerParser` ผลตรงกับที่ issue บันทึกไว้ทุกเคส คอลัมน์ "span" ดูจาก `spans` ที่ parser คืนมา คอลัมน์ "แก้ที่" มาจากการอ่านโค้ดของผู้ตรวจแผน และผู้ประสานงานยืนยันบรรทัดที่สำคัญแล้ว

| เคส | span | พังที่ไหน | แก้ที่ |
|---|---|---|---|
| A1, B1, B2 | ถูก | resolver ไม่เติมช่องที่ gazetteer ชี้ได้แถวเดียว | R1 หลัง resolve |
| Bangna | `Bangna` เป็น DISTRICT ถูก | `formSimilarity` ไม่เทียบชื่อละติน ทั้งสอง tuple ได้ 0 แถวแรกคือพระโขนงจึงชนะ ภาษาไทย `เขตบางนา … 10260` ได้บางนาอยู่แล้ว | R2 ใน `src/tagger/resolve.ts` |
| D1 | PHONE ถูกตัดที่ 10 หลัก | `normalizePhone` รับแค่ 9 ถึง 10 หลัก และ `recutPhone` ตั้งใจทิ้งเลขท้าย | R3 |
| C1 | NAME เริ่มที่ `เล่น` | โมเดลตัดขอบเอง `trimLabels` จึงไม่เห็นคำว่า `ชื่อ` | R4 มองย้อนใน raw |
| LINE | NAME รวม `(LINE: beam_shop)` | `attachBracketAfterName` ดึงทุกวงเล็บหลังชื่อเข้า NAME และ `GUIDE.md` ก็สอนแบบนั้น | R6 กฎ บวก NOTE เทรน |

สรุปคือ 7 ใน 8 กลุ่มแก้ได้โดยไม่เทรน เหลือแค่หมายเหตุที่ต้องเทรนใหม่

ข้อมูลเดิมมีหมายเหตุอยู่แล้วโดยไม่มีป้าย นับด้วย regex คำสัญญาณ (`ฝาก`, `รปภ`, `ป้อมยาม`, `Kerry`, `Flash`, `J&T`, `ปลายทาง`, `COD`, `โทรก่อน`, `วางไว้`, `LINE`, `ไลน์`, `ตู้ ป.ณ.`) ได้ 890 จาก 9,185 เรคอร์ดในชุดเทรน และ 242 จาก 2,448 ในชุด bench ถ้าเพิ่ม tag หมายเหตุโดยไม่ติดป้ายย้อนหลัง ราว 10% ของข้อมูลจะสอนว่าข้อความพวกนี้เป็น OTHER การติดป้ายย้อนหลังจึงเป็นงานบังคับ

## Appendix D. Alternatives rejected

- เทรน tagger ให้ติดป้ายหลายผู้รับเอง แพ้ เพราะ single-run decoding ต้องรื้อ และสัญญาณรหัสไปรษณีย์จากการวัดเบื้องต้นพอสำหรับ splitter ที่ไม่ต้องเทรน
- เพิ่ม tag NOTE โดยไม่ติดป้ายย้อนหลัง แพ้ เพราะราว 10% ของข้อมูลจะสอนสิ่งตรงข้าม
- ให้ `notes` เป็นทุกอย่างที่เหลือจาก OTHER แพ้ เพราะคำทักทายกับรายการสินค้าทำให้ช่องรก และสัญญากว้างทำให้ผู้ติดป้ายเห็นไม่ตรงกัน
- เปลี่ยน gold ให้เติมช่องแอดมินจาก `loc:` ทุกเรคอร์ด แพ้ เพราะต้อง re-baseline ทุกตัวเลขเดิม ขณะที่ `inferred` ให้ผลเดียวกันกับผู้ใช้โดยตัวเลขเดิมยังเทียบได้
- เปิดช่อง `company` จาก tag `ORG` ที่มีอยู่ เลื่อนไปรอบหน้า ไม่อยู่ในเงื่อนไขของ issue และเพิ่มขอบเขต
- hillclimb หลายรอบแบบเมื่อวาน แพ้ เพราะหลัง wave 3 ข้อมูลและโมเดลแบบใหม่ไม่ขยับ holdout เกิน noise

## Appendix E. ข้อตัดสินใจของ Peerasak

1. ขอบเขตของ `notes` ค่าเริ่มต้นคือเฉพาะข้อความที่มีผลต่อการส่ง ถ้าอยากเก็บรายการสินค้าด้วย บอกได้ จะเพิ่มเป็นหมวดในสัญญา แต่ผู้ติดป้ายจะเห็นไม่ตรงกันมากขึ้น
2. รูปผลลัพธ์หลายผู้รับ ค่าเริ่มต้นคือ `parse()` คืน `recipients` เป็นรายการเสมอ ปกติมีหนึ่งคน แล้วย้ายหน้าเดโมไปใช้ในการเปลี่ยนเดียวกัน ทางเลือกอื่นคือคงรูปเดิมแล้วใส่แค่ `multiple-recipients` ใน `warnings` ซึ่งเร็วกว่าแต่ผู้ใช้ต้องแยกเอง
3. ช่องที่เติมจาก gazetteer ค่าเริ่มต้นคือเติมลง `fields` เลยพร้อม `inferred` ถ้าอยากให้แยกเป็นช่องข้อเสนอที่ผู้ใช้ต้องกดยืนยัน บอกได้
4. R5 แปลงแป้น ค่าเริ่มต้นคือทำถ้าทันใน P1 แต่ไม่เป็นเงื่อนไขผ่าน
